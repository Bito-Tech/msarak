## منهجية التعامل مع المشكلات
عند ظهور أي مشكلة، نحدد أولًا نوعها ثم نعالجها في الطبقة التي تملكها فعليًا.
| النوع | مثال |
|---|---|
| متطلبات | اختلاف بين نسخة قديمة وحديثة من نموذج التقييم |
| تكامل | الواجهة والـBackend لا يستخدمان نفس العقد |
| بيانات | قاعدة البيانات تسمح بحالة غير صحيحة |
| أمان | الصلاحيات موزعة في أكثر من مكان |
| اختبار | QA يكشف حالة لم يغطيها التنفيذ |
| Git | أكثر من فرع عدل نفس الملف |
| محتوى | النص المعروض لا يطابق السلوك الحقيقي |
| بيئة | المشروع يحتوي أداة لا يستخدمها الفريق فعليًا |
> **المسار المعتمد:** السياق → المشكلة → الاكتشاف → القرار → التغيير → منطق الحل → النتيجة

# 01. ضبط المراجعة ومنع الدمج العشوائي
**السياق:** H-01 / PR #24 / GitHub Workflow  
**الأطراف:** جميع أعضاء الفريق
### المشكلة
وجود Pull Request لا يعني أن التغيير جاهز للدمج. كان لابد من منع دخول أي عمل إلى `main` بدون مراجعة وفحص.
### كيف اكتشفناها؟
أثناء تنظيم GitHub ظهر أن المراجعة يجب أن تتوزع حسب التخصص، مع وجود حالات يكون فيها صاحب العمل نفسه هو المراجع المحدد.
### القرار
اعتماد مسار ثابت:
```text
Issue
→ Branch
→ Pull Request
→ Review
→ CI
→ Merge
```
### ما الذي تغير؟
كل PR له مراجع حسب المجال، والـCI إلزامي، والدمج النهائي يتم بعد اكتمال شروط المراجعة فقط.
### منطق الحل
جودة التغيير أصبحت مرتبطة بمسار واضح يمكن تتبعه، وليس بمجرد انتهاء صاحبه من التنفيذ.
### النتيجة
أصبح `main` محميًا من الدمج العشوائي، وكل تغيير يمر بمراجعة وفحص قبل اعتماده.

# 02. تطوير نموذج التقييم
**السياق:** Assessment v1.2 / B-01 / H-03 / C-03 / B-04 / F-03  
**الأطراف:** الفريق كاملًا
### المشكلة
في البداية كان كل موقف يحتوي أربعة تصرفات ويختار الطالب التصرف الأقرب فقط، وهذا لم يكن يعبر بشكل كافٍ عن درجة ميله لبقية التصرفات.
### كيف اكتشفناها؟
أثناء مراجعة طريقة الإجابة ومحاولة جعل النتيجة تعتمد على معلومات أغنى من مجرد اختيار واحد.
### القرار
الإبقاء على اختيار أساسي واحد، مع إضافة تقييم اختياري لكل تصرف:
```text
+2  يشبهني جدًا
+1  يشبهني
 0  محايد / غير متأكد
-1  لا يشبهني
-2  لا يشبهني إطلاقًا
```
مع إضافة حالتي:
```text
none
cannot_judge
```
### ما الذي تغير؟
تغير نموذج الإجابة وطريقة التخزين والأوزان والحساب، ثم حدثنا العقود والمحتوى والواجهة والاختبارات لتتبع النموذج الجديد.
### منطق الحل
إضافة Rating غيرت معنى الإجابة نفسها، لذلك تعاملنا معها كتغيير في النظام كاملًا وليس كتعديل واجهة فقط.
### النتيجة
أصبح Backend والواجهة وقاعدة البيانات والمحتوى والاختبارات كلها تعمل على Assessment v1.2 نفسه.

**الأطراف:** مالك — Backend / عبدالله — QA

# 11. حل تعارضات Git في الملفات المشتركة
**السياق:** F-02 / PR #54  
**الأطراف:** أيمن — Frontend / حارث — Integration / تغييرات `main`
### المشكلة
أكثر من Feature عدل نفس الملفات المشتركة في وقت متقارب:
```text
resources/js/app.js
resources/views/layouts/app.blade.php
```
وعند تحديث الفرع من `main` ظهر Merge Conflict.
### كيف اكتشفناها؟
Git أوقف الدمج وطلب معالجة الملفات المتعارضة يدويًا.
### القرار
عدم اختيار نسخة أحد الطرفين وحذف الأخرى، بل مراجعة التعديلات ودمج المطلوب من الجانبين.
### ما الذي تغير؟
تم تحديث فرع F-02 من `main` وحل التعارضات، ثم إعادة مزامنته قبل الدمج النهائي.
ظهر في سجل العمل:
```text
Merge branch 'main' into feature/f-02-specializations-catalog-compare
```
ثم:
```text
Merge remote-tracking branch 'origin/main'
into feature/f-02-specializations-catalog-compare
```
### منطق الحل
الملفات المشتركة كانت تحتوي عملًا صحيحًا من أكثر من Feature، لذلك اختيار نسخة واحدة كان سيحذف عمل الطرف الآخر.
### النتيجة
تم الحفاظ على التعديلات المهمة من الجانبين، وأصبح الفرع متوافقًا مع آخر نسخة من `main` ثم تم دمجه بنجاح.
> ظهر نفس نمط إعادة مزامنة الفرع مع `main` في H-04 قبل الدمج النهائي، لكن دون توثيق كافٍ يثبت وجود Conflict يدوي على ملف محدد، لذلك لا نسجله كحالة Merge Conflict مستقلة.

# 12. تثبيت اختبار Rate Limit المتذبذب في CI
**السياق:** F-04 / Auth Tests / CI / Commit 93687a4  
**الأطراف:** Frontend / Authentication / CI Review
### المشكلة
أحد اختبارات Rate Limiting كان ينجح أحيانًا ويفشل أحيانًا أخرى رغم أن السلوك الفعلي لم يتغير.
الاختبار كان يقارن رسالة تحتوي عدد الثواني المتبقية مقارنة حرفية، بينما القيمة قادمة من عداد زمني حي:
```text
900
مقابل
899
```
فرق ثانية واحدة كان كافيًا لجعل اختبار صحيح وظيفيًا يظهر كفشل داخل CI.
### كيف اكتشفناها؟
ظهر السلوك بصورة متقطعة بين تشغيلات GitHub Actions؛ نفس التغيير قد ينجح في فحص ويفشل في فحص آخر بدون تعديل في منطق المصادقة نفسه.
### القرار
عدم إخفاء المشكلة بإعادة تشغيل CI حتى ينجح، وعدم إضعاف الاختبار بالكامل.
بدل ذلك تم تعديل الاختبار ليتحقق من المعنى الأمني المقصود، مع إزالة الاعتماد على الرقم اللحظي الذي يتغير مع الزمن.
### ما الذي تغير؟
تم تثبيت الاختبار عبر:
- إزالة المقارنة الصارمة للرقم المتغير داخل رسالة الانتظار.
- التأكد أن الردين يحتويان رسالة Rate Limit فعلية.
- تنظيف نافذة الـRate Limiter المطلوبة قبل حالات الاختبار حتى لا تتسرب حالة من خطوة إلى أخرى.
### منطق الحل
الاختبار الجيد يجب أن يفشل عندما يتغير السلوك المطلوب، لا عندما تمر ثانية إضافية أثناء التنفيذ.
وفي الوقت نفسه لا يصح تحويل الاختبار إلى مقارنة فضفاضة تسمح بمرور رد غير صحيح.
### النتيجة
أصبح الاختبار أكثر استقرارًا داخل CI مع بقاء التحقق الأمني نفسه قائمًا، وتم التخلص من Flaky Failure دون تغيير منطق Rate Limiting في التطبيق.

# 13. كشف انحرافات عقد النتائج بدل إخفائها باختبارات ناجحة
**السياق:** Q-04 / PR #72 / ResultContractVerificationTest / Result Contract  
**الأطراف:** عبدالله — QA / حارث — Integration / Backend + Frontend Contracts
### المشكلة
أثناء Q-04 اتضح أن الرحلة تعمل، لكن بعض تفاصيل الاستجابة الفعلية لا تطابق العقد المعتمد بالكامل.
ظهرت أربع حالات رئيسية:
```text
Q4-C1
similarity_score يظهر في JSON رغم أن العقد لا يطلب كشفه للواجهة.
Q4-C2
أول Complete يعيد 200 بدل 201، بينما العقد يميز بين أول إنشاء وإعادة الطلب.
Q4-C3
Result History لا يحتوي top_domains وrecommendation_names.
Q4-C4
Result payload لا يحتوي top_domains.
```
المشكلة الأخطر لم تكن فقط وجود الاختلاف، بل أن كتابة اختبار يطابق التنفيذ الحالي كانت ستجعل السلوك المخالف للعقد يبدو صحيحًا.
### كيف اكتشفناها؟
أثناء Verification المستقلة في Q-04، عندما قورنت الاستجابات الفعلية بالعقد بدل الاكتفاء بأن الرحلة تعمل وأن الاختبارات القديمة خضراء.
### القرار
عدم تعديل توقع الاختبار ليتبع السلوك الخاطئ، وعدم إصلاح Production Code داخل Q-04 لأنها مهمة تحقق وليست مهمة تنفيذ.
تم تثبيت الاختبارات على السلوك التعاقدي المقصود، ووضع الحالات المخالفة كـPending/Skipped مع توثيقها كـContract Deviations تحتاج تتبعًا منفصلًا.
### ما الذي تغير؟
أصبحت الحالات الأربع مسجلة صراحة في تقرير Q-04 بدل أن تضيع داخل نتيجة اختبار عامة.
كما تم التفريق بين:
```text
Confirmed deviation
```
وبين:
```text
NOT VERIFIED
```
في حالة Concurrency التي لم يثبت فيها Bug فعلي.
### منطق الحل
وظيفة Verification هي كشف الفرق بين العقد والتنفيذ، لا إعادة تعريف العقد لكي تصبح الاختبارات خضراء.
واختبار Pending يوضح أن لدينا سلوكًا مطلوبًا لم يتحقق بعد، بينما اختبار يوافق الخطأ يحوله إلى Regression مقبول مستقبلًا.
### النتيجة
أصبحت انحرافات Result Contract ظاهرة وقابلة للتتبع، وانتقلت مسؤولية حسمها إلى Q-05 / Release Gate بدل إخفائها داخل Test Suite ناجحة شكليًا.

# 14. منع الـSeeder من تغيير نسخة تقييم منشورة
**السياق:** Assessment Versions / B-05 / Q-05 / Issue: Seeder Immutability  
**الأطراف:** مالك — Backend / عبدالله — Verification / حارث — Integration
### المشكلة
تبين أن AssessmentQuestionBankSeeder يمكن عند إعادة تشغيله أن يصل إلى نسخة تقييم قديمة ويحدث بياناتها أو يعيد تفعيلها.
هذا يتعارض مباشرة مع القاعدة التي يعتمد عليها النظام:
```text
Published / Used Assessment Version = Immutable
```
لأن Session أو Result تاريخية يجب أن تبقى قابلة للتفسير بنفس النسخة التي بنيت عليها.
### كيف اكتشفناها؟
ظهرت أثناء مراجعة دورة حياة Assessment Versions وتجهيز التحقق النهائي للإصدار، وليس من خلال رحلة الطالب العادية فقط.
المشكلة لا تظهر بالضرورة عند تشغيل التطبيق مرة واحدة، لكنها تظهر عند إعادة Seed أو تحديث البيانات لاحقًا.
### القرار
اعتبار النسخة المنشورة أو المستخدمة ثابتة تاريخيًا.
أي تغيير جديد في بنك الأسئلة لا يعدل النسخة القديمة، بل ينشأ من خلال Version جديدة.
### ما الذي تغير؟
تم فتح Issue مستقلة ومحددة النطاق لمعالجة منطق Seeder / Assessment Version lifecycle وإضافة اختبارات تثبت أن:
- النسخة القديمة لا تتغير.
- النسخة القديمة لا تعود Active عند وجود نسخة أحدث.
- published_at لا يتغير بسبب إعادة Seed.
- النتائج والجلسات التاريخية تظل مرتبطة بنفس النسخة.
### منطق الحل
الـSeeder أداة لإعادة بناء البيانات، لكنه لا يملك حق إعادة كتابة التاريخ.
وثبات النسخ المنشورة أهم من راحة تحديث Seeder واحد، لأن أي تعديل على نسخة مستخدمة يغير معنى البيانات التاريخية.
### النتيجة
تحولت المشكلة من خطر مخفي في عملية التهيئة إلى قاعدة Lifecycle واضحة وIssue قابلة للاختبار قبل Release Gate.

# 15. عدم اعتماد Evidence قديمة بعد تحرك main
**السياق:** Q-05 / PR #73 / Clean Clone / H-05  
**الأطراف:** أيمن — Q-05 Stage A / عبدالله — Final Verification / حارث — Release Integration
### المشكلة
تم تنفيذ Clean Clone ناجح في Q-05 على Commit محدد، ثم تغير main بعده بدخول أعمال جديدة.
كانت نتيجة Clean Clone صحيحة وقت تنفيذها، لكنها لم تعد تثبت أن آخر نسخة من المشروع نفسها اجتازت التحقق.
المثال الفعلي كان Evidence على:
```text
04315888128d300fb43c675498331041aaf18a47
350 tests
2034 assertions
```
بينما main تحرك بعد ذلك بدخول Q-04 وتغييرات أخرى.
### كيف اكتشفناها؟
أثناء مراجعة PR #73 وربط Q-05 بـH-05، عندما قورنت قيمة SHA الموجودة في Evidence مع أحدث main بدل الاكتفاء بعنوان PR الذي يقول إن Clean Clone ناجح.
### القرار
ربط كل Evidence مؤثرة بـCommit SHA واضح.
أي Clean Clone نُفذت قبل آخر تغيير Release-scoped تعتبر:
```text
Interim Evidence
```
وليست Final Release Evidence.
### ما الذي تغير؟
تم الفصل بين:
- Clean Clone تاريخية تثبت أن المشروع كان قابلًا للبناء عند SHA معين.
- Final Clean Clone يجب أن تنفذ لاحقًا على Release Candidate نفسه.
كما أصبح Final RC SHA جزءًا إلزاميًا من H-05 قبل إنشاء v1.0.0.
### منطق الحل
التحقق لا ينتقل تلقائيًا من Commit إلى Commit آخر.
حتى لو كان التغيير اللاحق صغيرًا، لا يمكن القول إن SHA جديدة اجتازت Clean Clone لمجرد أن SHA أقدم نجحت.
### النتيجة
أصبح الدليل مربوطًا بالنسخة التي اختبرت فعلًا، ومنعنا اعتماد نتيجة صحيحة تاريخيًا كدليل نهائي لنسخة لم تُختبر بعد.

# 16. تقسيم Q-05 بين أكثر من عضو بدون إغلاقها جزئيًا
**السياق:** Q-05 / Issue #42 / PR #73  
**الأطراف:** أيمن — Stage A / عبدالله — Verification / حارث — Integration
### المشكلة
Q-05 كبيرة وتجمع بين تجهيز خطط التحقق، Clean Clone، System Testing، Security Regression، Integration وDefect Retest.
نفذ أيمن جزءًا منها أولًا، بينما بقيت الرحلات والتحقق النهائي لعبدالله.

### كيف اكتشفناها؟

# 17. اكتمال Logout في Backend وغيابه من الواجهة
**السياق:** H-02 / F-05 / UX-01 Audit / UX-02  
**الأطراف:** حارث — Integration / أيمن — Frontend
### المشكلة
كان تسجيل الخروج منفذًا فعليًا على الخادم عبر:
```text
POST /logout
```
مع إنهاء Session وتجديد CSRF token، لكن لا يوجد في الواجهة أي زر أو رابط يستدعي المسار.
بالتالي كانت الوظيفة موجودة تقنيًا وغير مكتملة من منظور المستخدم.
### كيف اكتشفناها؟
أثناء مراجعة UX-01 لكل resources/views/، وتم توثيقها في docs/design/audit.md كحالة خارج نطاق تحسين الهوية البصرية وتحتاج Issue مستقلة.
### القرار
عدم تعديل Backend لأنه يعمل بالفعل، وعدم دفن الوظيفة داخل UX-01.
تم فتح UX-02 كمهمة Frontend صغيرة تستخدم المسار الحالي كما هو:
```text
POST /logout
- @csrf
  ```
### ما الذي تغير؟
تم تحديد أن التعديل يجب أن يبقى في طبقة الواجهة:
- Logout واضح في Desktop.
- Logout واضح في Mobile.
- لا GET logout.
- لا Session logic جديد.
- لا Routes جديدة.
### منطق الحل
وجود Endpoint لا يعني اكتمال Feature إذا لم توجد وسيلة للمستخدم للوصول إليه.
وفي المقابل، عدم وجود الزر لا يبرر إعادة كتابة Authentication الموجود بشكل صحيح.
### النتيجة
تحولت الفجوة من ملاحظة في Audit إلى مهمة محددة بحدود واضحة تكمل الوظيفة دون توسيع نطاق المصادقة.
